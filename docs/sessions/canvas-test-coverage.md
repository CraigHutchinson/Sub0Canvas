# Follow-up session for test coverage on canvas

Status is backlogged as of 2026-11-19. [U8 quality signals](../USE_CASES.md#u8-u11-further-consumers-design-targets) · [Runtime evidence](canvas-runtime-evidence.md) · [Scoped viewer reads](../AUTHORING.md#31-live-views-scoped-queries-in-events-out-patches-on-the-page)

## User view and entry points

Turn on Testing in the source view for a selected run, revision and test scope. Show line or range coverage in the gutter and a summary at block level. Distinguish coverage observed in passing tests, failing tests only, both, and no hits in fully measured executable code. Distinguish partial or unavailable capture from zero hits. Label aggregate-only imports and mark historical observations on edited code. Drill from a range to its measured tests, their outcomes and available assertions or traces. From the check or test list, select a test to highlight its measured ranges and open an assertion. An assertion can link to its own location and any recorded stack or value-producing observation. An agent can request the same scoped summary and detail by file, block, test or run.

## Existing tooling and integration trade-offs

| Prior art | Fit and limitation |
|---|---|
| GCC gcov | The Windows C++ spike already produced line and branch counts. Use compiler output, including JSON where available. The harness must isolate profiles per selected test and join them to runner outcomes before merging. Separate processes offer simple isolation with startup and storage costs. First compare with one aggregate profile. [gcov options](https://gcc.gnu.org/onlinedocs/gcc/Invoking-Gcov.html) · [Profile relocation](https://gcc.gnu.org/onlinedocs/gcc/Cross-profiling.html) |
| Clang source-based coverage | JSON export includes source regions and supports branch detail. Per-test attribution still needs profile isolation or runner boundaries. Retain build and tool versions and prefer a versioned import over treating raw profiles as durable interchange. [Clang coverage guide](https://clang.llvm.org/docs/SourceBasedCodeCoverage.html) |
| VS Code Testing API | Run-scoped file summaries, expansion on demand and optional per-test detail are a precedent for the viewer. This also exposes an integration choice later: an editor client can consume the same scoped results that power the canvas viewer. [Testing API](https://code.visualstudio.com/api/extension-guides/testing#test-coverage) · [Per-test detail API](https://code.visualstudio.com/api/references/vscode-api#TestRunProfile) |
| Test assertions and mutation analysis | GoogleTest exposes test-part results and listener hooks, which represent events the framework emits. Check each harness's pass-event semantics before promising every assertion. PIT uses coverage to select tests for a behavior-changing mutation, then measures whether the tests detect it. This provides a separate sensitivity signal at the cost of extra builds or executions and interpretation of surviving or equivalent mutations. [GoogleTest test parts](https://google.github.io/googletest/reference/testing.html#TestPartResult) · [PIT concepts](https://pitest.org/quickstart/basic_concepts/) |
| Other backends | Coverage.py already shows which test contexts exercised a line. Rust reuses LLVM coverage tooling, with tool-version compatibility to check. Playwright can collect Chromium JavaScript and CSS coverage, where attribution needs runner boundaries and bundled ranges need source mapping before they appear on original source. Evaluate these with a concrete receiving harness. [Coverage.py contexts](https://coverage.readthedocs.io/en/latest/contexts.html) · [Rust coverage](https://doc.rust-lang.org/rustc/instrument-coverage.html) · [Playwright coverage](https://playwright.dev/docs/api/class-coverage) |

Execution, assertions and behavior sensitivity are three different signals. A passing test can run code whose output it never checks. A failing test can contain earlier passing assertions and leave later assertions unreached. Capturing a stack as a check reports its result may miss a value-producing frame that has already returned. Capturing useful assertion evidence may require a bounded observation around evaluation of the checked expression, with setup, shared helpers and background work kept in their recorded scope. Display “assertion evidence unavailable” when the link is missing. A mutation result can reveal a gap for a specific changed behavior and tested set.

## Receiving path

1. After the C++ trace slice, use the existing Sub0Squad calculator as the named consumer. The current TAP runner iterates its registry in one process and reports each test outcome. The spike's gcov profile was aggregate. Try a harness-only named-case entry point and isolated profiles before adding in-process recording. Capture one passing and one failing test on the same build and include a shared range, a failing-only range, an untouched executable range and missing capture. Compare launch time, artifact size, attribution, and agreement with the normal gate under instrumentation. Leave the normal gate path available.
2. Import only what the view receives. Scope observations by build or candidate, file revision, run, test identity, outcome and capture completeness. Begin with file and block summaries and on-demand ranges and test IDs. Reuse layer links and historical source reads. Evaluate a format extension through B0 only if the prototype needs it. V1a's file, layer and detail reads are the likely viewer seam. Measure reverse lookup and source expansion without shipping the whole test-by-range relation in each turn bundle. Verify a later edit cannot make old data appear current.
3. Add assertion-level capture only as a separate measured slice. Start with a test containing a passing assertion, a failure, and an assertion not reached. Verify which values, frames or evaluated expressions the harness can really observe. Compare targeted capture with a fixture that executes code outside an asserted behavior. Consider mutation evidence later if a named consumer needs sensitivity beyond execution and recorded checks.

The major work stays backlogged. The first receiving result is an honest per-test overlay and bidirectional drill-down for one C++ fixture. Assertion tracing, mutation analysis, CI ingestion and other language adapters remain separate slices.
