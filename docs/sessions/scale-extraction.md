# Follow-up session: one unbounded extraction of an active area, and its anonymised mirror

Backlog: item 16 (low priority). Design: [SCALE.md](../SCALE.md) 6.1 (profile B), [BACKBONE.md](../BACKBONE.md) section 6, [MIRROR.md](../MIRROR.md), [CHANGE_VIEWS.md](../CHANGE_VIEWS.md).

## Goal
Stress the history and the viewer with one real extraction instead of fixed-size windows: an active area of the owner's private monorepo over about a month, with its commits, its pull requests and, where the forge allows, their comments and reviews, and the bug tickets whose traces land in it. The point is to find what breaks as the scope grows, not to ship a feature. A week of one area (21 commits, 1,218 files) touched 190 of 14,036 blocks and only 3 of them twice, so it cannot show the cases that matter: a block changed by several commits in different places, a change confined to part of a block, and long-lived blocks whose history must stay readable.

Second product, same session: a codified anonymiser. It reads an extraction and writes a mirror that keeps the organisation of the work (tree, spans, which commit and pull request touched which blocks and hunks, the similarity between a block's versions) and none of the work (identifiers, strings, comments, subjects, authors become placeholder text). Only the mirror may be stored or committed; the extraction stays in git-ignored `out/` and is deleted after use.

## Left
1. **Pick the area by churn, not by size.** A whole-bundle snapshot grows as files times turns, so choose a narrow hot subtree (hundreds of files, a hundred or more turns) over a wide cold one. The first count of per-directory churn over 30 days is slow on a monorepo; run it once and keep the numbers.
2. **A scope that extends back in time.** `sub0canvas snapshot` takes `--history N` today. Add a way to grow the window dynamically (older revisions on demand, by date or count) so a view can start recent and reach back, without re-reading what it already holds. Conceptually the turns begin at the first commit; in practice the window is bounded and the viewer says where it stops.
3. **Compact unchanged history.** A turn repeats every file; as turns grow the list must not. Carry only what changed (the per-turn `eventsFrom` and files by content id are in [SCALE.md](../SCALE.md) 6.1, point 2) and fold runs of turns that did not touch the selected block or area into one entry.
4. **Block-to-commit tracing.** From a block, list the commits that changed it, in order, and where a commit changed only a sub-range of the block, the range. Today a commit anchors to the whole block (`commits` layer) and an event says `edited` without a span; hunk ranges are the missing datum.
5. **A pull request layer.** From local git alone: the pull request number, branch and merge subject in a merge commit's header. From the forge, read-only through the logged-in `gh` CLI into `out/`: title, body, comment and review counts, review threads anchored to files and lines. Anchor each review thread to the blocks at the commit it was made on. Forge calls carry only repository and pull request numbers; the owner approves the first run.
6. **A tracker layer.** Bug tickets are where a failure is described by its evidence: a log line or stack trace, a symptom message, the files and functions named in it, the versions affected and the ports (the same fix backported to other lines). Read them through the owner's tracker connector (read-only, into `out/`), search by the area's paths and symbols and by the messages that recur, and anchor each ticket to blocks three ways: a stack frame or file:line that resolves to a block at the revision the ticket names (the source-anchor resolver in [BACKBONE.md](../BACKBONE.md) handles a moved block), a quoted symbol or message that a block's text contains, and the commits and pull requests that reference the ticket key. Keep the evidence structured (frames as path, symbol, line; message templates with their variable parts masked), so tickets that share a message or a frame group together and a block shows every ticket that has hit it. A ticket's claim about the code can be wrong (a note that a function is unreachable on a path where the source says otherwise); keep the claim and the checked outcome apart, as in [sessions/canvas-prose-verification.md](canvas-prose-verification.md). The tracker's names, keys and links never enter this tree.
7. **The anonymiser.** One deterministic, seeded pass: file and directory names, identifiers, strings and comments become generated word soup of the same length and token shape; line counts, block spans, nesting, and the Jaccard similarity of a block's versions are preserved so reconciliation behaves as it did on the original; commit subjects, pull request titles, bodies, comments and authors become placeholder text with the same graph (who touched what, in which order, which review thread sits on which block); tracker keys become generated keys, stack frames keep their depth and resolve to the mirror's blocks, and message templates keep their shape and recurrence counts. A leak check runs over the mirror with the local private-terms guard before anything is written outside `out/`. Success is measured, not asserted: the library's block counts, event kinds and fan-out on the mirror match the extraction to within a stated tolerance.
8. **Gate on shape.** Record the extraction's numbers (files, turns, blocks, commits per block, hunks per block, pull requests, threads, tickets per block, frames per ticket) and the mirror's, and add the mirror's counts as the representative minimums for `tools/scale-check.mjs`, so a later build is judged against a realistic size.

## Done means
* One command makes the extraction of a named area and window into `out/`, and the viewer opens it on the latest turn with a block's commit list, the changed sub-ranges and the pull request layer.
* The measured table (snapshot time and memory, bundle size, viewer parse, heap, click latency in a foreground window, DOM nodes) is in [SCALE.md](../SCALE.md) under profile B, numbers only.
* The anonymiser's output loads in the viewer, passes the leak check, and its metrics agree with the extraction's; its seed and generator are in the tree, its input never is.
* The faults found are in the backlog as items, each with the number that exposed it.

## Environment and constraints
* The owner's standing rules ([AGENTS.md](../../AGENTS.md)): a public repository never names the private one; its location stays in untracked `.git/sub0canvas/repos.json`; nothing leaves the machine; confirm before pushing.
* Build with GCC 14 or later (the code uses `<print>`); the Strawberry GCC 13 cannot. Use short build paths on Windows.
* Click timing is only valid in a foreground window; a throttled pane steps in whole seconds.
* `gh` is logged in to the owner's forge host with repository scope; use read-only calls, and keep the responses in `out/`.
